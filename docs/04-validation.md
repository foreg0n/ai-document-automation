# Этап 4. Проверка полей и причины ручной проверки

## Что добавлено

После ответа LLM приложение проверяет поля обычным кодом Python.
Такая проверка называется детерминированной: одинаковые поля, предупреждения
чтения и дата сравнения дают одинаковый результат.

В отчёте два возможных статуса:

- `passed` — реализованные правила не нашли проблем;
- `needs_review` — есть причины посмотреть документ вручную.

`passed` не доказывает совпадение полей с PDF. Например, правдоподобная, но
выдуманная моделью сумма может пройти проверку формата. Здесь нет сверки
значений с исходным текстом, проверки контрагентов или одобрения оплаты.

## Запуск без ключа API

Демонстрация на эталонных данных первого этапа:

```powershell
.\.venv\Scripts\python.exe -m tools.demo_validation --as-of 2026-10-30 --overwrite
```

Она создаёт пять отчётов в `output/validation-demo`. Четыре записи проходят
правила; у четвёртой отсутствует сумма, поэтому она получает `needs_review`.
Каждый отчёт помечен `input_kind: "reference_fixture"`. Это демонстрация
проверок на известных значениях, а не результат работы или оценка LLM.

Дубликат проходит эти проверки полей. Поиск дубликатов добавим на этапе 5.
Успешно завершённая демонстрация возвращает код 0, включая ожидаемый пример
`needs_review`.

## Проверка сохранённых результатов модели

Если у тебя уже есть файлы `*.fields.json` после реального запуска этапа 3:

```powershell
.\.venv\Scripts\python.exe -m document_automation validate output/invoices --as-of 2026-10-30
```

Или один файл:

```powershell
.\.venv\Scripts\python.exe -m document_automation validate output/invoices/01_invoice_pln.pdf.fields.json --overwrite
```

По умолчанию отчёты сохраняются в `output/validation`. Папка может содержать
другие JSON: команда выбирает только `*.fields.json` и не заходит в подпапки.
Один JSON-файл можно указать с любым именем.

`validate` работает локально, без `.env`, ключа и обращения к модели.
Если рядом с `*.fields.json` есть соответствующий `*.meta.json`, команда читает
из него предупреждения о страницах без текста. Неверные метаданные вызывают
ошибку, чтобы потеря предупреждений не превратилась в ложный успешный результат.

При отсутствии метаданных проверяются только сами поля. В отчёте будет
`text_warnings_checked: false`: полнота чтения PDF в таком запуске не проверялась.
Исходные поля и метаданные сохраняются; новый отчёт содержит результат перепроверки.

## Правила версии invoice_demo_v1

| Проверка | Причина ручной проверки |
| --- | --- |
| Значения всех пяти полей | `null`, пустое значение или заглушка вроде `N/A` |
| Пробелы по краям | Значение требует осознанной нормализации |
| Формат даты | Строго `YYYY-MM-DD`, без времени или сокращений |
| Календарь | Дата должна существовать: `2026-02-30` невозможна |
| Будущая дата | Дата счёта позже даты сравнения |
| Формат суммы | Строка с точкой, двумя десятичными знаками, без разделителей тысяч |
| Положительная сумма | Нулевая или отрицательная сумма требует проверки |
| Валюта | Три заглавные латинские буквы и поддержка в текущем списке |
| Полнота текста | Предупреждение о любой странице без извлечённого текста |

Список поддерживаемых валют сейчас: PLN, EUR, USD. Например, CHF получает
`unsupported_currency`, а не утверждение, что такой валюты не существует.

Это правила учебного проекта. Корректировочный счёт с отрицательной суммой,
нулевой документ или счёт с будущей датой могут быть настоящими документами.
Наш код помечает их для проверки, поскольку такие сценарии пока не поддержаны.
Даты, суммы и валюты автоматически не исправляются.

## validate_invoice()

Находится в `document_automation/validation.py`.

Функция получает словарь полей, дату сравнения `reference_date` и предупреждения
чтения. Она не читает файлы, не вызывает модель и не изменяет исходный словарь.
Это позволяет использовать те же правила позже в интерфейсе или API.

Внутренняя функция `add()` добавляет очередную причину в список. Проверки
собирают все найденные проблемы, чтобы пользователь видел их сразу.

Для даты используются две проверки:

1. Регулярное выражение проверяет точное написание `YYYY-MM-DD`.
2. `date.fromisoformat()` проверяет, существует ли такой день в календаре.

Регулярное выражение — шаблон допустимых символов и их порядка. Оно само по
себе не знает, сколько дней в феврале. Поэтому второй шаг необходим.

После этого дата сравнивается с `reference_date`.
`--as-of 2026-10-30` задаёт дату явно. Без этой опции CLI берёт локальную дату
компьютера один раз на весь пакет. Повторяя проверку с той же датой, можно
воспроизвести старый отчёт.

## Зачем нужен Decimal

Сначала шаблон суммы проверяет её запись: например, `"1234.50"` допустимо,
а `"1,234.50"`, `"1234,50"` и `"1e3"` требуют проверки формата.

Затем выполняется точное сравнение:

```python
elif Decimal(value) <= 0:
    add("non_positive_amount", "total_amount", "...")
```

`Decimal` представляет десятичные значения точно. Обычный `float` хранит их
в двоичной форме и не всегда представляет десятичную дробь без погрешности.
Мы не округляем значение модели и не превращаем отсутствующую сумму в ноль.

## ValidationIssue и ValidationReport

`ValidationIssue` хранит одну причину:

- `code` — короткий стабильный код для программы;
- `field` — имя поля или `None`, если проблема относится ко всему документу;
- `message` — понятное объяснение.

`ValidationReport` хранит дату сравнения и кортеж причин. Свойство
`requires_review` показывает, есть ли хотя бы одна причина, а `status` возвращает
нужный статус. `to_dict()` готовит данные для записи в JSON.

Пример фрагмента отчёта:

```json
{
  "rules_version": "invoice_demo_v1",
  "reference_date": "2026-10-30",
  "status": "needs_review",
  "requires_review": true,
  "issues": [
    {
      "code": "missing_value",
      "field": "total_amount",
      "message": "Required invoice value is missing; check the source document."
    }
  ]
}
```

Код причины поможет будущему интерфейсу выделить нужное поле и показать
сообщение. Отдельная версия правил поможет понять, по каким правилам был
создан отчёт.

## validate_saved_fields() и process_pdf()

`validate_saved_fields()` находится в `validation_files.py`. Она читает
сохранённый JSON, проверяет базовую структуру этапа 3, загружает доступные
метаданные и вызывает `validate_invoice()`. Затем сохраняет отдельный отчёт.

Невалидный JSON, повторяющиеся ключи или неправильные типы нарушают договор
этапа 3 и считаются ошибкой обработки. Отсутствующая сумма, представленная
правильным JSON `null`, обрабатывается успешно, но требует ручной проверки.

`process_pdf()` теперь автоматически вызывает тот же валидатор сразу после
получения полей от модели. При реальном запуске создаются три файла:

- `*.fields.json` — исходные поля ответа;
- `*.meta.json` — сведения об обработке и статус проверки;
- `*.validation.json` — причины и версия правил.

В `--dry-run` создаётся только запрос-превью: полей для проверки ещё нет.
Перед запросом API проверяется занятость всех трёх имён результата.

## Коды завершения

| Код | Значение для process и validate |
| --- | --- |
| 0 | Все результаты обработаны и не требуют проверки |
| 1 | Ошибка чтения, API или записи; она имеет приоритет над кодом 3 |
| 2 | Неверные аргументы команды |
| 3 | Результаты сохранены, но хотя бы один требует ручной проверки |

Код 3 помогает будущей автоматизации отличить документ для проверки от ошибки
программы. `extract` и `--dry-run` сохраняют прежнее поведение кодов завершения.
